# Native public-research schedules

The agent creator can open **Agent options → Agent schedule** in chat, choose weekdays, local time and an IANA timezone, then save or pause the schedule. Run now works while paused. Recent runs link to ordinary, owner-scoped Brain conversations. All briefings remain drafts requiring review.

The public-research pilot only supports active agents without company knowledge, action tools, MCP servers, skills, service-account delegation or personal context. Every run verifies the active human owner and current agent configuration and explicitly selects web search only. It uses the existing chat execution and usage path; unknown model pricing remains unpriced, and budgets are not enforced by this feature.

## Reviewed project drafts

The schedule API can instead bind an active human-owned agent to one project for private, review-required drafts. An active organization administrator who owns the agent and has direct or organization-wide project access must select a specific configured model and explicitly approve the current scope. Team-only project access is not supported by this first slice. A service-account agent, attached action tool, MCP server, skill or user-context injection is refused. No project run can post to Slack, search the public web, execute code, call another action, or share its conversation with the project. The normal project and source ACLs still apply, and source permission failures must not be treated as proof that a source is empty.

1. `GET /api/v1/agents/{id}/schedule/project-grant/preview?projectId=...` returns the agent knowledge, project sources and linked collection, selected model/provider and a fingerprint. Review the source reach and model destination before approving.
2. `POST /api/v1/agents/{id}/schedule/project-grant` with that exact `projectId` and `fingerprint` approves only that snapshot. The server checks that the scope has not changed between preview and approval. No live company-data grants are created by installing this code.
3. `PUT /api/v1/agents/{id}/schedule` with `projectId` enables or changes a project schedule. A missing `projectId` preserves its existing mode; `null` chooses public research. Omit both Slack fields for a project schedule. OAuth/PAT callers additionally need `project:read`.
4. `DELETE .../schedule/project-grant` revokes approval. Subsequent runs fail closed and the schedule pauses. Revocation cannot recall a run already underway. Re-approval, a model or agent change, or a project scope/instructions change invalidates the old binding; review again and save the schedule to bind the new grant.

The worker rechecks the live identity, admin role, project access, scope and selected model before the model call. Python enforces the existing scoped retrieval/record permissions and an explicit retrieval-only registry; it checks the selected model's configuration fingerprint before passing project content to it. The conversation is private and linked to the project. Schedule audit logs contain actor, organization, agent, project, grant, run and outcome metadata, not prompts, source contents or tool results. Model calls still use the existing usage pipeline; missing model or cost data is not a verified budget. A crash or ambiguous response still pauses for reconciliation. This first slice has no per-project Slack delivery, action tool execution, system/service-agent execution or independently bounded budgets.

An organization administrator can enable **Send to Slack** in Agent schedule, select an existing agent bot and paste a Slack channel link or ID. The bot must already be connected through **Workspace → Bots** and invited to that channel. The UI links to bot management; no channel-list scopes are required. Delivery currently uses the existing single-organization Slack registry. Tokens never enter schedule requests or the ledger. Messages are labelled drafts, suppress special Slack mentions, and include a Brain link. The Brain conversation itself is not shared by posting its link. Save changed settings before using Run now.

The existing KV store persists settings and the last twenty run references. Compare-and-set claims prevent concurrent replicas from executing the same tick. Missed ticks coalesce into one reporting window. A conversation ID is saved before model execution. Uncertain model/delivery outcomes pause automation and require an administrator to inspect the conversation and Slack before deliberately running again; there is no automatic retry. This avoids duplicate posts after ambiguous network failures. The worker starts after HTTP listening, waits for query health before claiming, and drains before its storage/auth dependencies stop.

Schedule endpoints are documented in the OpenAPI specification. OAuth reads need `agent:read`; saving needs `agent:read`, `agent:write` and `agent:execute`; manual execution needs `agent:read` and `agent:execute`. Agent ownership is checked separately.

The creator can choose **Change agent picture** from agent options in chat or the saved agent builder. Choose a PNG, JPEG or WebP (up to 5 MiB), preview it, then Save. Remove also requires Save. The server validates actual bytes, limits decoded pixels and re-encodes a 512px square WebP without metadata. Small image bytes use the existing persistent KV store; private API reads recheck organization, current agent visibility and the active image version. Deployment-owned assets remain supported. This updates the picture in Brain; Slack application icons are managed separately in Slack.

Persistent KV storage is required. Persistent volumes are not backups: configure off-host backups and test restoration separately.
